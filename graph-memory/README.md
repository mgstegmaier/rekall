# graph-memory

Semantic memory over your wiki (the `wiki/` folder inside the vault that `[vault].path` in `rekall.toml` names). Below, `$WIKI` is that wiki folder (`.venv/bin/python ../rekall_config.py WIKI` prints it) and `<data>` is `[data].path`. A `UserPromptSubmit` hook searches a local SQLite index and injects the top wiki hits into every Claude Code prompt, so sessions get wiki context without grepping.

Vendored from [Glitch-Cat-Club/graph-memory-starter](https://github.com/Glitch-Cat-Club/graph-memory-starter) (see `LICENSE-upstream`), with these local changes: frontmatter is stripped before chunking, each page's `title`/`description` frontmatter becomes its own searchable row and prefixes its chunks, dated chunks are weighted toward recent material, a chunk with a strong keyword hit is admitted without clearing the meaning threshold, and `distil.py` takes `--under <subfolder>` to scope distillation.

## How it works

- `build_index.py --corpus "$WIKI"` chunks every wiki page on headings (h1–h3, packed to ~1600 chars), prefixes each chunk's index text with the page's title and description (the deterministic form of contextual retrieval; the stored excerpt stays the raw section), embeds it locally with BGE-small (fastembed, CPU, no API; `[index] embedding_model` in `rekall.toml` can name another fastembed model, and the next run re-embeds everything with it), and writes keyword (FTS5) + vector indexes to `<data>/rag.db`. Runs are incremental by default (a content hash per file in the `files` table; only new/changed/deleted files are touched, seconds on a typical day). The first run each Sunday promotes itself to a full rebuild (`last_full` date in the `meta` table, so a Mac asleep at the scheduled hour still gets its weekly full after waking). That automatic full reuses every vector whose text is unchanged and finishes in seconds. An explicit `--full` drops everything and re-embeds all of it: on 2026-11-01 it took 47 minutes for 15,254 chunks at a load average of about 5 (5.4 chunks per second, no vectors reused). An embedding-model change needs no `--full`: the next run rebuilds in full and re-embeds every chunk with the new model, and `meta.model` names it only in the commit that holds those vectors. A full rebuild that has kept failing for more than 7 days (`last_full` older than that) is retried on every run until one commits. Each rebuild is one SQLite transaction, so recall keeps reading the last good index until it commits, and a failed or killed run changes nothing. A DB without the `files` table (pre-incremental) upgrades itself with one automatic full build.
- `recall_hook.py` runs on every prompt: keyword + semantic search, rank-fused and weighted toward recent material, up to 5 hits injected as context (1500-char cap on the whole injection: header, labels, graph block and notices included) under a two-line header that marks them as quoted data from ingested sources, never instructions. A hit must clear the meaning threshold (cosine 0.68), or be a strong keyword hit: one of the keyword leg's top 3 chunks that holds every rare name or ID in the prompt (a word written with a capital or a digit, found in at most 30 chunks, e.g. a person's name or `SNOW-1234`), which the embedding alone scores low. The prompt's first word counts only when it is all-caps or has a digit, since grammar capitalises it ("Please ...", "Debug this"), so a one-word name prompt gets no keyword pass. A lowercase or common word never passes on keywords alone, and that holds when the model is unavailable or mismatched too: with no meaning leg, only strong keyword hits are admitted. The Claude Desktop `search_wiki` tool uses the same rule. It skips prompts the harness wrote (task notifications, command output, subagent hand-backs, idle notices and messages from other sessions, "Tool loaded.", session continuations, skill bodies; the list is `harness_prompt.py`), button replies, and bare acknowledgements. It fails open: no failure blocks a prompt. An empty result injects nothing, and a failure shows `rekall unavailable: <reason>` (see the hooks paragraph below). You'll see `memory: N hits` in the session when it fires.
- Recency: each chunk carries a date (`chunks.date`), picked by `build_index.chunk_date`: the newest of the chunk's `[[YYYY-MM-DD]]` citations and a `YYYY-MM-DD` filename prefix (meetings, session digests), else frontmatter `date`. `search.fuse` scales a dated chunk's score by `0.9 + 0.1 × 0.5^(age / 90 days)`, so a 90-day-old chunk keeps 95 percent and nothing drops below 90 percent. Rank-fusion scores sit close together, so that range is enough to break near-ties without making date the main sort. Undated chunks are not scaled. `HALF_LIFE_DAYS` and `RECENCY_FLOOR` at the top of `search.py` are the knobs; `EVAL_NO_RECENCY=1` turns it off in `eval/sample_hits.py` for an A/B.
- `search.py "your question"` is the CLI test tool; it shows which leg (keyword/meaning) found each hit.
- `distil.py "$WIKI" --under meetings` runs one `claude -p` call per meeting note, extracting question + verbatim-quote entries into `<data>/distilled/`, outside this repo because distillates carry meeting and company content. Quotes are validated word-for-word against the source or dropped. A note whose answer quotes something the note doesn't say gets a strike at once. A failed call or an empty or unparseable answer gets a strike only when another note in the same run succeeded, so an outage can't strike every note. A timeout, a missing `claude` or a sign-in failure never strikes. Two strikes on the same content quarantine the note until it changes. SHA256 state in `<data>/distilled/.state.json` skips unchanged notes on re-runs.

## Graph layer

`build_graph.py --corpus "$WIKI"` builds a deterministic knowledge graph into the same `rag.db`: one entity per wiki page (type from its folder, name/description from frontmatter), one untyped `mentions` edge per `[[wikilink]]`, plus typed relations where a page states them. No LLM involved. `--extra` folders (none needed since 2026-09-04: digests live in `wiki/sessions/`, inside the corpus) become `session`-type entities whose wikilinks become edges too, so "when did I last touch X" is answerable from the graph; wiki pages always win a slug collision, and spaced link text like `[[Familiar Cost Watch]]` resolves to its hyphenated slug. `graph_recall.py "question"` seeds entities named in the question and walks 2 hops with a recursive SQL query (~30ms). The recall hook runs this as a third leg and appends the triples as a "Wiki graph:" block.

## Session digest

`digest/session_end.py` runs on the `SessionEnd` hook: it filters the transcript down to your words and the replies (tool calls, results, and thinking dropped), stages it under `digest/pending/`, and spawns a detached `claude -p` (sonnet) that writes a structured digest (`digest/digest-prompt.md` is the voice) into the vault at `wiki/sessions/YYYY-MM-DD.md`. A session that closes again gets a continuation entry that records only what changed and links back to the earlier entry. Sessions shorter than `min_turns` (default 5) are skipped. Failures never block a session close; they land in `digest/log/digest.log` and the staged file stays for retry. A staged file whose `claude` call fails three times, in runs where another file succeeded, moves to `digest/pending/failed/`, which nothing reads; move it back to retry. The reindex sweeps `wiki/sessions/` with the rest of the corpus, so past sessions become searchable memory. This complements `/wrap-up`, which stays the deliberate close-out.

## MCP server (Claude Desktop)

`mcp_server.py` is a read-only stdio MCP server for clients with no `UserPromptSubmit` hook (Claude Desktop chat). It wraps the recall hook's search and adds no search logic of its own. Two tools:

- `search_wiki(query, section)`: up to 5 chunks labeled `[file § section]` with full text, plus graph facts as `subject -[predicate]-> object (doc)`. `section` is optional: when given, only chunks under that heading are kept (exact match, ignoring case) and graph facts are left out. A reply is capped at 10,000 characters.
- `read_page(name, offset)`: one full note from anywhere in the vault (wiki pages, `guide/` docs, `today.md`), by file name without `.md` or by vault-relative `.md` path, skipping dot-folders; a candidate list of paths if a bare name is ambiguous. A reply is capped at 20,000 characters, and a longer page ends with the `offset` to resume from. Backslashes and `..` are rejected.

`install.sh` installs `mcp==1.30.0` into the venv and writes the `rekall` entry into Claude Desktop's `claude_desktop_config.json` (`~/Library/Application Support/Claude/` on macOS, `%APPDATA%\Claude\` on Windows). It skips that step when Claude Desktop isn't installed, and `install.sh --uninstall` removes the entry. Restart Claude Desktop after either. The entry it writes:

```json
{
  "mcpServers": {
    "rekall": {
      "command": "/path/to/rekall/graph-memory/.venv/bin/python",
      "args": ["/path/to/rekall/graph-memory/mcp_server.py"]
    }
  }
}
```

To check it, run `python3 graph-memory/test_mcp_server.py`, which calls both tools against the live index. `test_mcp_server_fixture.py` does the same against a temp index built from `vault-template/`, so it needs no install. In Claude Desktop, the server shows under Settings > Developer; if it reports a failure there, the log is `~/Library/Logs/Claude/mcp-server-rekall.log`.

## Operations

| Task | Command |
|------|---------|
| Refresh index + graph | `./reindex.sh` (runs hourly from the `com.rekall.wiki-reindex` schedule; it retries staged digests, distils new meeting and `raw/` notes, then runs incremental index and graph builds, with the week's first Sunday run auto-promoted to a full rebuild) |
| Force a full rebuild | `.venv/bin/python build_index.py --corpus "$WIKI" --full` |
| Test a query | `.venv/bin/python search.py "what's next on the billing migration"` |
| Test graph recall | `.venv/bin/python graph_recall.py "who is involved in the billing migration"` |
| Distil new meeting notes | `.venv/bin/python distil.py "$WIKI" --under meetings` |
| Check the LaunchAgent | `launchctl list \| grep wiki-reindex`; log at `logs/wiki-reindex.log` in the state folder (`[data].state`, default `~/.config/rekall`) |
| Check the last run | `launchctl print gui/$UID/com.rekall.wiki-reindex \| grep "last exit code"`; `grep FAILED <state>/logs/wiki-reindex.log` (a non-zero exit means a builder failed and the FAILED line names it; exit 2 with `FAILED config` means the wiki path is empty or missing) |
| Check digest failures | `cat digest/log/digest.log`; staged retries sit in `digest/pending/` |

The index is disposable. If anything looks wrong, delete `rag.db` and run `./reindex.sh`. The index builders only read the wiki. `reindex.sh` does write markdown into the vault (session digests drained from `digest/pending/`), and distillates go to `<data>/distilled/`. The SQLite DB lives in `<data>`, on local disk, so a synced vault never syncs it.

If a rebuild fails with unreadable files, OneDrive has dehydrated the vault: mark your vault folder as "Always Keep on This Device" in Finder. The run logs `FAILED build_index` and leaves the last good index in place.

`eval/` measures the hook: `sample_hits.py` freezes a set of real prompts from Claude Code transcripts and records what each leg returns, `judge.py` labels every returned item with a headless Haiku call and scores precision per leg, position, and predicate (pass two label dirs to average two judge passes; one pass wobbles about 5 points). Every retrieval change since 2026-09-12 was decided on it; numbers and decisions live in `docs/plans/2026-09-12-typed-wiki-graph.md` and `docs/plans/2026-09-13-contextual-retrieval.md`. A model-written context sentence per chunk (`contextualize.py`) was tried and measured flat at 300 prompts, then removed; the deterministic title/description prefix in `build_index.py` stays.

Tests: every `test_*.py` is a plain script (`python3 graph-memory/test_recall_hook.py`), and `pytest -q` from the repo root runs them all. With `REKALL_CONFIG` unset, the root `conftest.py` points them at a scratch `rekall.toml` and a copy of `vault-template/`, so pytest never touches your install; the two tests that need a built index (`test_search.py`, `test_mcp_server.py`) skip there.

`eval/gate.py` is the pre-merge check, deterministic and free: 32 hand-written prompts in `eval/gate_prompts.json`, each with the page and section it should find, run through the hook's own `hits()`. It prints recall@4 and exits 1 when that falls 2 points or more below `eval/gate_baseline.json`. Run it before any PR that touches `search.py`, `build_index.py` or `recall_hook.py`, with the venv's python and your real config (not the pytest scratch one, which has no index): `cd graph-memory && .venv/bin/python eval/gate.py`. When a change is meant to move the number, rerun with `--write-baseline` and commit the new baseline in the same PR. The prompts are written against the maintainer's own project pages, so on another vault, replace them and write a fresh baseline.

`eval/judged_gate.py` is the second pre-merge check, for changes meant to cut noise or that could. It runs real prompts whose candidate sections a judge has already graded (2 directly relevant, 1 related, 0 not useful) and prints how many prompts with a relevant section still get one (`useful`), junk sections shown per prompt, and how many prompts that need nothing get nothing (`silent-ok`). It exits 1 when `useful` falls 2 points below its baseline; junk and silence are printed but don't fail it. The prompts and grades live in `<data>/eval/judged_prompts.json` beside `rag.db`, never in the repo, because real prompts carry names and work details; the baseline sits beside them. Each prompt keeps its UTC timestamp, as Claude Code's transcripts record it, and runs as its local day saw it: session digests, meetings and daily notes dated from that local day on are dropped, since they often describe the prompt's own session. Comparing on the UTC date instead would let an evening prompt's own digest through. A change that surfaces sections nobody graded shows them as `unjudged`; past 20 percent the gate warns and won't write a baseline, and `--unjudged` lists them with each prompt's local time, to grade by hand (add each to its case's `grades`). Run it with the venv's python: without `fastembed` the meaning leg is off, and the gate stops instead of reporting a false drop. Without a graded set of your own the gate exits with a message, so on another vault it is opt-in.

`digest/session_end.py` also logs which injected context a session used, through `digest/recall_use.py`. Each close appends one **line** to `recall-use.jsonl` beside the digest log (`<data>/digest/log/`): `{"v": 2, "session", "ts", "injections": [...]}`, where `ts` is the close time. A session with no rekall injections writes no line. An **injection** is one rekall attachment in the transcript (memory hits, a "Wiki graph:" block, or both): `attachment_uuid`; `trigger_uuid`, the event that triggered it; `trigger`, one of `typed` (a user event), `queued` (a `queued_command` prompt delivered mid-task), `meta` (an `isMeta` event such as a subagent hand-back) or `null` when the parent chain doesn't reach one; `origin`, the queued prompt's raw `origin.kind` (`human`, `peer`, `task-notification`, or `null`); `prompt`, the trigger's text with reminder blocks stripped, cut to 200 characters (`""` for an image-only prompt); `labels`, one `{file, section, read, reused}` per `[file § section]` hit; and `graph`, one `{doc, read}` per document the graph block cited. The trigger is found by walking the transcript's `parentUuid` chain from the attachment (`logicalParentUuid` across a compaction), passing over other attachments, system events and the image and skill-body events written after their prompt. Who wrote it is left to the reader: a `queued` trigger is typed when `origin` is `"human"`; a `meta` trigger is harness-written; a `typed` trigger is harness-written when `harness_prompt.is_harness(prompt)` says so, except that `<command-message>` markup is a slash command someone typed and an empty prompt is an image-only prompt someone typed. `read` and `reused` count only inside the injection's **window**, from its attachment to the next typed or meta prompt: `read` when the session Read a file ending in that path, `reused` when a reply holds two of the excerpt's five longest words. A queued prompt doesn't end a window, so a Read after it counts for both the earlier injection and the queued one. A resumed session closes, and writes, more than once, so keep the last line per session. A line with no `v` is v1: its prompts are paired one turn late and its `read` and `reused` span the whole session. `python3 graph-memory/digest/recall_use.py --show <transcript>` prints the injections of a session still open; `--rebuild` appends a v2 line (with the v1 `ts` and `"rebuilt": true`) for each session whose last line is v1 and whose transcript is still on disk, after copying the old file once to `recall-use.v1-backup.jsonl`, and is safe to run again. No Claude call; any failure lands in `digest.log` and the digest goes on.

Hooks are registered in `~/.claude/settings.json`: `UserPromptSubmit` → `recall_hook.py`, `SessionEnd` → `digest/session_end.py`. Both fail open. The command in `hooks.json` checks the script exists before running it, because a bare `python missing.py` exits 2 and Claude Code reads exit 2 from `UserPromptSubmit` as a block on every prompt. When recall can't run (script or venv missing, no `rag.db`, broken config, search error) you see `rekall unavailable: <reason>` and a line lands in `logs/hook.log` in the state folder; the prompt goes through without context. Setup on a new machine: copy `rekall.example.toml` to `rekall.toml` at the repo root and set the vault and data paths, then `python3 -m venv .venv && .venv/bin/pip install -r requirements.txt && ./fetch_model.sh && ./reindex.sh`, then add both hooks (`install.sh` does all of this, including the hooks). The full guided install is `SETUP.md`.
